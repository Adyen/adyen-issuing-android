    Migrating from SDK versions prior to 0.4.0¶

    Guidance for upgrading existing integrations from provisioning-sdk 0.3.x and earlier to 0.6.0+, which is built on Google's Unified Push Provisioning.

    Migrating straight to the Card Provisioning Sessions SDK?

    If you are on < 0.4.0 and your end goal is the Card Provisioning Sessions SDK, you can skip this migration entirely. The Card Provisioning Sessions SDK uses provisioning-sdk internally and exposes a different client API — the createSdkOutput() / OpcProvider / direct-SDK distinctions never surface in your code. Follow the Card Provisioning Sessions SDK — Getting Started instead. This page is for integrations that intend to stay on the Card Provisioning SDK.

    Why upgrade¶

    The primary reason to move to 0.6.0+ is support for Google's Unified Push Provisioning (UPP).

    Every release up to and including the 0.4.x line is built on Google's legacy Tap and Pay push-provisioning API. Google has deprecated that API and replaced it with Unified Push Provisioning, which can save a card to the user's Google account rather than only to the specific device that ran the provisioning flow. 0.6.0 is the first release built on UPP.

    How much work the upgrade involves depends on where you are starting from:

    • Already on 0.4.x — you are on the current client API, so moving to 0.6.0+ is a dependency version bump with no code changes. Skip to step 4.
    • On < 0.4.0 — you have a breaking-change API migration to do as well as the version bump, because the pre-0.4.0 createSdkOutput() + provision(sdkInput, …) API cannot be preserved on top of UPP. That migration is the subject of this page.

    The current API is built around a single OpcProvider callback that the SDK invokes when it requires the Opaque Payment Card (OPC) data, rather than requiring the application to orchestrate that exchange. Pre-0.4.0 integrations call createSdkOutput(), send the resulting sdkOutput to the backend to retrieve the OPC value from Adyen, and only then call provision(sdkInput, cardDisplayName, cardAddress). From 0.4.0 you pass an OpcProvider to a single provision(cardDisplayName, cardAddress, opcProvider) call, and the SDK performs the round-trip internally.

    Secondary benefits picked up along the way:

    • Fewer steps at the call site. One provision(cardDisplayName, cardAddress, opcProvider) call replaces the two-stage createSdkOutput → backend call → provision(sdkInput, …) sequence.
    • Backend integration is unchanged. The two networkTokenActivationData endpoints (GET for sdkInput, POST for OPC) still carry the same payloads — only the timing of their invocation from the client changes.
    • Unified error handling. Failures inside the OPC retrieval surface through the single ProvisionResult returned from the new overload, rather than being split across CreateSdkOutputResult and ProvisionResult.

    Breaking changes¶

    Both pre-0.4.0 entry points were deprecated in 0.4.0 and are removed in 0.6.0. They are the two halves of one legacy sequence, so neither survives on its own.

    Code still calling them stops compiling, on purpose. Because 0.6.0+ is built on Google's Unified Push Provisioning API, the Opaque Payment Card is created during the provisioning flow rather than supplied up-front, so the sdkInput parameter of the old provision(...) overload has nothing left to carry. sdkOutput cannot be pre-built either: it bundles values that first exist mid-flow — the session id Google supplies, and the single-use ephemeral key your backend's response is encrypted to. An sdkOutput obtained ahead of the flow would carry no session id, so your backend would not create a Google Opaque Payment Card for it. Nothing would be able to decrypt the response either — exchanging it with your backend could only waste a network-token activation. The old calls are therefore removed rather than left to fail at runtime: your build stops at exactly the call sites that need migrating, instead of shipping a provisioning flow that fails on a user's device.

    API Status Replacement
    CardProvisioning.createSdkOutput(): CreateSdkOutputResult @Deprecated in 0.4.0; removed in 0.6.0 Not needed — the new provision(...) overload performs the equivalent step internally, at the point in the flow where Google requires it.
    CardProvisioning.provision(sdkInput, cardDisplayName, cardAddress): ProvisionResult @Deprecated in 0.4.0; removed in 0.6.0 provision(cardDisplayName, cardAddress, opcProvider): ProvisionResult
    CreateSdkOutputResult (sealed interface and all Success / Failure.* variants) @Deprecated in 0.4.0; removed in 0.6.0 Failure cases that previously surfaced here now flow through ProvisionResult.Failure.
    ProvisionResult.Failure.CreateSdkOutputNotCalled @Deprecated in 0.4.0; removed in 0.6.0 No replacement — the precondition it reported cannot arise once the OPC exchange is owned by the SDK.

    Migrating to provision(cardDisplayName, cardAddress, opcProvider) also means supplying an OpcProvider implementation that performs the OPC backend call your own code used to orchestrate.

    OpcProvider interface¶

    OpcProvider is a fun interface (single abstract method, so it accepts a SAM lambda):

    public fun interface OpcProvider {
    public suspend fun fetchOpc(
        paymentInstrumentId: String,
        sdkOutput: String,
    ): String
}

    The SDK invokes fetchOpc once per provision(...) call, passing the paymentInstrumentId of the card being provisioned and a newly issued sdkOutput. The implementation must return the base64-encoded OPC string from the backend. Exceptions thrown from fetchOpc propagate as a ProvisionResult.Failure, allowing retries and error mapping to be handled alongside the rest of the provisioning error handling.

    Unlike the pre-0.4.0 sequence — where the backend call sat in your own code and could take as long as you allowed — fetchOpc runs inside Google's provisioning flow and is bounded by a 20-second timeout, after which the attempt fails with ProvisionResult.Failure.OpcFetchError. Code moved out of the old two-stage sequence should have its client timeouts checked against that budget.

    fetchOpc is a suspend function, so this is also a good opportunity to move the call onto a coroutine-aware HTTP client if it was previously blocking. The SDK cancels the call when the budget expires, but only a suspending client can act on that and abort the request — a blocking call runs to completion in the background with its result discarded.

    Step-by-step migration¶

    1. Replace createSdkOutput() callers with an OpcProvider¶

    Anywhere the OPC round-trip was previously invoked manually:

    val sdkOutputResult = cardProvisioning.createSdkOutput()
val sdkOutput = (sdkOutputResult as CreateSdkOutputResult.Success).sdkOutput
val opc = backend.requestOpaquePaymentCardData(paymentInstrumentId, sdkOutput).sdkInput

    …relocate the same backend call into a lambda that the SDK invokes on your behalf:

    val opcProvider = OpcProvider { paymentInstrumentId, sdkOutput ->
    backend.requestOpaquePaymentCardData(paymentInstrumentId, sdkOutput).sdkInput
}

    If OpcProvider is the only argument requiring SAM conversion at the call site, it can also be inlined as a named lambda — see step 2.

    2. Update the provision(...) call site¶

    Before — pre-0.4.0 sequence with the backend exchange in client code:

    // 1. Request sdkOutput from the SDK.
val sdkOutputResult = cardProvisioning.createSdkOutput()
val sdkOutput = (sdkOutputResult as CreateSdkOutputResult.Success).sdkOutput

// 2. Call the backend to exchange sdkOutput for the card data.
val opc = backend.requestOpaquePaymentCardData(paymentInstrumentId, sdkOutput).sdkInput

// 3. Pass the card data back to the SDK to complete provisioning.
val provisionResult = cardProvisioning.provision(
    sdkInput = opc,
    cardDisplayName = "John Doe",
    cardAddress = CardAddress(),
)

    After — single call with an OpcProvider:

    val provisionResult = cardProvisioning.provision(
    cardDisplayName = "John Doe",
    cardAddress = CardAddress(),
    opcProvider = { paymentInstrumentId, sdkOutput ->
        backend.requestOpaquePaymentCardData(paymentInstrumentId, sdkOutput).sdkInput
    },
)

    3. Remove the now-unused CreateSdkOutputResult handling¶

    Any when expression that exhausted CreateSdkOutputResult.Success / CreateSdkOutputResult.Failure.* branches must be removed — the type no longer exists in 0.6.0. Failures that previously surfaced there are now reflected in the ProvisionResult returned by the new provision(...) — update the existing ProvisionResult mapping if it does not already cover those cases. A when over ProvisionResult.Failure that branched on CreateSdkOutputNotCalled needs that branch dropped for the same reason.

    4. Update the dependency version¶

    Move to 0.6.0 or later — earlier releases are built on the legacy Tap and Pay API and do not include the UPP implementation. Update the published version in the module's build.gradle.kts:

    dependencies {
    implementation("com.adyen.issuing.provisioning:provisioning-sdk:0.6.0")
}

    Bumping to 0.6.0+ also changes how Google's Push Provisioning API library reaches your build: the published provisioning-sdk artifact now bundles play-services-tapandpay. If you previously obtained the artifact from Google and hosted it in your local Maven cache or an internal repository for the SDK, you can remove that direct dependency — provided no other part of your app uses the library. The hosting setup is no longer needed for the SDK, but your app must still be allowlisted by Google — see Google Push Provisioning API Access.

    The removed APIs are off the binary surface entirely, so a library compiled against < 0.4.0 and used transitively no longer links against 0.6.0+ — a call it makes to createSdkOutput() or provision(sdkInput, …) raises NoSuchMethodError. Any such dependency has to be rebuilt against the current API before you can upgrade. Code already on the 0.4.0+ API has no dependency on either removed member and needs no changes.

    What remains unchanged¶

    • CardProvisioning.create(sdkInput, activityProvider) — unchanged. The sdkInput returned by the GET /networkTokenActivationData backend call is still passed at construction time.
    • canProvision() — unchanged signature and CanProvisionResult variants.
    • CardAddress — same package, same fields.
    • Backend endpoints — the two networkTokenActivationData calls are still issued; only the timing of their invocation on the client changes.
